🔍 How Flannel Works

Flannel creates an overlay network that enables pod-to-pod communication across different nodes. Here's the step-by-step process:

  1. Pod Network Assignment: Each node gets a unique subnet from the cluster CIDR (10.42.0.0/16)
  2. VXLAN Encapsulation: Flannel encapsulates pod traffic in VXLAN packets
  3. Route Discovery: Flannel maintains routing tables via etcd or Kubernetes API
  4. Traffic Forwarding: Packets are forwarded through the physical network to destination nodes

⚠️ Why Same Network Interface (enp0s8) is Critical

Flannel needs consistent network interface naming across all nodes for proper routing and discovery!

🎯 Interface Consistency

All nodes must use the same physical interface name (enp0s8) for Flannel to create consistent routing rules and maintain network topology.

🗺️ Route Tables

Flannel creates route entries that reference specific interface names. Different names break the routing logic.

📍 Node Discovery

Flannel uses interface names to identify which interface to bind VXLAN tunnels to for inter-node communication.

🔧 Configuration Sync

The flannel configuration assumes uniform interface naming for automatic network setup across the cluster.

🛠️ Network Configuration Details

Flannel VXLAN Backend Configuration:

{ "Network": "10.42.0.0/16", "Backend": { "Type": "vxlan", "VNI": 1, "Port": 8472 } }

Required Ports:

• 8472/UDP - VXLAN traffic between nodes • 6443/TCP - Kubernetes API server • 10250/TCP - Kubelet API • 2379-2380/TCP - etcd (if using embedded etcd)

🚨 Common Network Issues & Solutions

❌ Problems:

  • Different interface names (eth0 vs enp0s8)
  • Firewall blocking VXLAN port 8472
  • Incorrect node IP detection
  • Missing route entries
  • MTU mismatch issues

✅ Solutions:

  • Standardize interface naming across nodes
  • Open required firewall ports
  • Use --node-ip flag explicitly
  • Verify flannel daemonset is running
  • Set correct MTU (usually 1450 for VXLAN)
